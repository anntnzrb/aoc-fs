# 2017 journal

Per-day learning log: the key idea, what surprised us, measurements, and
lessons that later days should apply. No puzzle text, no answers.

## Day 01

- Key idea: both parts compare each element of a circular sequence with the
  element a fixed step ahead; one `matchSum step` helper over an array with a
  modulo index covers both (step 1, then step n/2).
- Surprise: none in the algorithm. Fantomas reflowed a multi-line `Seq.fold`
  onto one line, so the first gate failed on format drift.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Run `nix develop -c just fmt` before `just check`; the gate rejects any
    layout Fantomas would change.
  - Part-2 fixtures need both answers: work out each example's part-1 answer
    by hand from the statement, never from solution output.
  - The fixture runner adds one test per fixture; check that the test count
    rises by the number of fixtures you wrote, which proves they ran.
  - Write the `Input` parser as an all-or-nothing `Result` fold that rejects
    empty input and bad characters; solvers derive their own arrays from it.

## Day 02

- Key idea: model a non-empty row as `Row of first * rest` so the extrema
  fold has a natural seed; part 2 enumerates unordered pairs with a prefix
  fold (each value pairs only with the values already seen).
- Surprise: nothing algorithmic; the statement's "exactly one evenly dividing
  pair per row" makes summing every exact quotient equal to the pair's one.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - First-plus-rest shapes avoid sentinel extrema and partial `List.min`.
  - Check the input's magnitudes before choosing a numeric type: `int` or
    `int64` unless the values can overflow them. Day 02 used `bigint` for
    four-digit values, which is unneeded weight (YAGNI).
  - A parser-only `.fsx` probe in scratch (`dotnet fsi --exec`) is a cheap way
    to exercise parser edge cases without touching tracked tests.

## Day 03

- Key idea: one lazy coordinate stream (`Seq.initInfinite` legs, flattened
  with `Seq.concat`, positions by `Seq.scan`) serves both parts: part 1 takes
  the n-th position, part 2 folds a sparse `Map` of written cells over it.
- Surprise: none; the input is a single number, so `Input` holds one
  single-case DU and the coordinates stay in the solver.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - `Seq.scan` emits its seed first; skip it explicitly when a second
    computation seeds that state itself.
  - Sparse grids: `Map.tryFind |> Option.defaultValue` for absent
    neighbours; neighbour offsets come from a list expression.
  - Traversal order, coordinates and caches belong to the solver, never to
    `Input`.

## Day 04

- Key idea: one private `uniqueBy key` helper (map, `Set.ofList`, compare
  counts) answers both parts: `id` for exact duplicates, sorted letters as
  the canonical key for anagrams.
- Surprise: none; all fixtures and both first submissions passed.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Canonical keys must keep multiplicity: a sorted character list does, a
    character set does not.
  - Keep the original words in `Input`; canonical keys belong to the solver.
  - One tuple fold aggregates both parts' counts in a single traversal.

## Day 05

- Key idea: one `steps update` simulator over a fresh local array per part;
  only the offset update rule differs between parts.
- Surprise: `TryParse` overload ambiguity needed an explicit `string`
  annotation on the parser helper.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Annotate parameters at overloaded .NET API boundaries (`Int32.TryParse`
    and friends) so inference picks the intended overload.
  - Simulations that mutate indexed state copy the parsed list into a local
    array per part, so one part cannot contaminate the next; a `while` loop
    with local `mutable` is the accepted hot-loop shape.
  - Guard both index bounds before converting a position to an array index.

## Day 06

- Key idea: simulate with `Seq.unfold` carrying a `Map` from configuration
  to first-visit cycle; the first repeat yields both the cycle count and the
  loop length (current cycle minus first visit).
- Surprise: `AGENTS.md` named `render` as a top-level export; it is
  `Answers.render`. Fixed in the architecture notes.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Immutable DUs and lists are structural `Map`/`Set` keys out of the box;
    store first-visit indices when the period matters, not just a `Set`.
  - Use `>` (not `>=`) in an argmax fold when the lowest index wins ties.
  - Even redistribution is quotient plus a circular-prefix remainder; no
    per-block stepping is needed.

## Day 07

- Key idea: the root is the one name that is nobody's child (set
  difference); part 2 totals sub-towers bottom-up, then descends into the
  outlier child carrying the majority total as the target.
- Surprise: Fantomas also scanned F# probes under ignored `.cache/`, so a
  scratch `.fsx` written during a gate run caused format drift. Fixed with a
  `.fantomasignore` excluding `.cache/`.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Trust the statement's guarantees ("exactly one program has the wrong
    weight"); guarding every impossible shape bloated day 07 to 90+ lines.
    Fewer lines win: return an `Error` for the impossible case, do not model
    it.
  - Tail-recursive explicit frontier plus a reversed visit list gives a
    children-before-parents order without non-tail tree recursion.
  - `List.groupBy` then sorting groups by size finds the majority and the
    outlier in one expression.

## Day 08

- Key idea: a register machine as a tuple fold over an immutable `Map`
  (absent reads default to zero); the all-time maximum rides along in the
  same fold.
- Surprise: none; the subtlety is that registers named only in conditions
  still exist (value zero) for the final maximum.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Model an instruction set's operators as DUs and evaluate them with one
    `match`; the parser maps tokens to cases.
  - When values can all be negative, seed a final extremum with `None`, not
    a zero floor; a running maximum only needs the changed value per step.

# 2017 journal

Per-day learning log: the key idea, what surprised us, measurements, and
lessons that later days should apply. No puzzle text, no answers.

## Day 01

- Key idea: both parts compare each element of a circular sequence with the
  element a fixed step ahead; one `matchSum step` helper over an array with a
  modulo index covers both (step 1, then step n/2).
- Surprise: none in the algorithm. Fantomas reflowed a multi-line `Seq.fold`
  onto one line, so the first gate failed on format drift.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Run `nix develop -c just fmt` before `just check`; the gate rejects any
    layout Fantomas would change.
  - Part-2 fixtures need both answers: work out each example's part-1 answer
    by hand from the statement, never from solution output.
  - The fixture runner adds one test per fixture; check that the test count
    rises by the number of fixtures you wrote, which proves they ran.
  - Write the `Input` parser as an all-or-nothing `Result` fold that rejects
    empty input and bad characters; solvers derive their own arrays from it.

## Day 02

- Key idea: model a non-empty row as `Row of first * rest` so the extrema
  fold has a natural seed; part 2 enumerates unordered pairs with a prefix
  fold (each value pairs only with the values already seen).
- Surprise: nothing algorithmic; the statement's "exactly one evenly dividing
  pair per row" makes summing every exact quotient equal to the pair's one.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - First-plus-rest shapes avoid sentinel extrema and partial `List.min`.
  - Check the input's magnitudes before choosing a numeric type: `int` or
    `int64` unless the values can overflow them. Day 02 used `bigint` for
    four-digit values, which is unneeded weight (YAGNI).
  - A parser-only `.fsx` probe in scratch (`dotnet fsi --exec`) is a cheap way
    to exercise parser edge cases without touching tracked tests.

## Day 03

- Key idea: one lazy coordinate stream (`Seq.initInfinite` legs, flattened
  with `Seq.concat`, positions by `Seq.scan`) serves both parts: part 1 takes
  the n-th position, part 2 folds a sparse `Map` of written cells over it.
- Surprise: none; the input is a single number, so `Input` holds one
  single-case DU and the coordinates stay in the solver.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - `Seq.scan` emits its seed first; skip it explicitly when a second
    computation seeds that state itself.
  - Sparse grids: `Map.tryFind |> Option.defaultValue` for absent
    neighbours; neighbour offsets come from a list expression.
  - Traversal order, coordinates and caches belong to the solver, never to
    `Input`.

## Day 04

- Key idea: one private `uniqueBy key` helper (map, `Set.ofList`, compare
  counts) answers both parts: `id` for exact duplicates, sorted letters as
  the canonical key for anagrams.
- Surprise: none; all fixtures and both first submissions passed.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Canonical keys must keep multiplicity: a sorted character list does, a
    character set does not.
  - Keep the original words in `Input`; canonical keys belong to the solver.
  - One tuple fold aggregates both parts' counts in a single traversal.

## Day 05

- Key idea: one `steps update` simulator over a fresh local array per part;
  only the offset update rule differs between parts.
- Surprise: `TryParse` overload ambiguity needed an explicit `string`
  annotation on the parser helper.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Annotate parameters at overloaded .NET API boundaries (`Int32.TryParse`
    and friends) so inference picks the intended overload.
  - Simulations that mutate indexed state copy the parsed list into a local
    array per part, so one part cannot contaminate the next; a `while` loop
    with local `mutable` is the accepted hot-loop shape.
  - Guard both index bounds before converting a position to an array index.

## Day 06

- Key idea: simulate with `Seq.unfold` carrying a `Map` from configuration
  to first-visit cycle; the first repeat yields both the cycle count and the
  loop length (current cycle minus first visit).
- Surprise: `AGENTS.md` named `render` as a top-level export; it is
  `Answers.render`. Fixed in the architecture notes.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Immutable DUs and lists are structural `Map`/`Set` keys out of the box;
    store first-visit indices when the period matters, not just a `Set`.
  - Use `>` (not `>=`) in an argmax fold when the lowest index wins ties.
  - Even redistribution is quotient plus a circular-prefix remainder; no
    per-block stepping is needed.

## Day 07

- Key idea: the root is the one name that is nobody's child (set
  difference); part 2 totals sub-towers bottom-up, then descends into the
  outlier child carrying the majority total as the target.
- Surprise: Fantomas also scanned F# probes under ignored `.cache/`, so a
  scratch `.fsx` written during a gate run caused format drift. Fixed with a
  `.fantomasignore` excluding `.cache/`.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Trust the statement's guarantees ("exactly one program has the wrong
    weight"); guarding every impossible shape bloated day 07 to 90+ lines.
    Fewer lines win: return an `Error` for the impossible case, do not model
    it.
  - Tail-recursive explicit frontier plus a reversed visit list gives a
    children-before-parents order without non-tail tree recursion.
  - `List.groupBy` then sorting groups by size finds the majority and the
    outlier in one expression.

## Day 08

- Key idea: a register machine as a tuple fold over an immutable `Map`
  (absent reads default to zero); the all-time maximum rides along in the
  same fold.
- Surprise: none; the subtlety is that registers named only in conditions
  still exist (value zero) for the final maximum.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Model an instruction set's operators as DUs and evaluate them with one
    `match`; the parser maps tokens to cases.
  - When values can all be negative, seed a final extremum with `None`, not
    a zero floor; a running maximum only needs the changed value per step.

## Day 09

- Key idea: the first nested grammar, so FParsec entered (1.1.1, pinned in
  `Directory.Packages.props`). `Input` parses a `Group | Garbage` tree with
  cancellation removed at the parser boundary; one `Seq.unfold` over an
  explicit `(item, depth)` frontier yields both totals.
- Surprise: `open FParsec` brings its own `Error`/`Success`, shadowing
  `Result.Error`.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - FParsec is available for nested or recursive grammars. Open it only in
    `Input.fs` and qualify `Result.Ok`/`Result.Error` there.
  - Create the forwarded parser (`createParserForwardedToRef`) inside
    `parse`, so the recursive grammar needs no module-level mutable state.
  - When examples are fragments but the input needs a root container, wrap
    them and work out the container's contribution by hand.

## Day 10

- Key idea: one `twist rounds lengths` reversal fold over a local 256-cell
  array (position and skip carried across rounds) serves the single numeric
  round and the 64-round ASCII hash; `Array.chunkBySize 16`, `fold (^^^)`
  and invariant `x2` formatting finish the dense hash.
- Surprise: part 2 reads the same line as raw text, so `Input` must keep the
  original text alongside its optional numeric reading.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Keep the raw text in `Input` when a later part may reinterpret the line;
    the numeric view is optional, not the model.
  - Wrapped circular operations are easy to mis-derive by hand: write the
    fixture derivation out step by step in scratch, and never copy solver
    output into an expectation.
  - Solvers never construct `Input` wrappers; they unwrap them.
  - A second consumer of this hash would trigger the shared-module review
    (AGENTS.md: the second occurrence triggers a review, not automatic
    extraction).

## Day 11

- Key idea: hex moves in two axial coordinates; the distance follows from
  the adjacency invariant (each step changes two of `q`, `r`, `-q-r` by one,
  so the largest magnitude is both a lower bound and reachable). No search.
- Surprise: none; part 2 adds a running maximum to the same fold.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Finite direction grammars are DUs in `Input`; geometry (coordinates,
    distance) stays in the solver.
  - Carry prefix extrema in the fold state instead of materialising a
    `scan`.
  - Justify a closed-form shortcut with a one-line comment at the decision
    point.

## Day 12

- Key idea: connected components are repeated reachability with one
  visited `Set` carried across start nodes; part 1 is the size of the
  component holding program 0, part 2 counts how many starts open a new one.
- Surprise: the first version built `ProgramId 0u` inside the solver;
  review sent it back. The solver now unwraps ids into its own
  `Map<uint32, uint32 list>`.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - A constant the solver needs (start node 0) lives in the solver's
    unwrapped working type, never as a freshly built `Input` value.
  - FParsec `sepBy1`/`sepEndBy1` plus `eof` cover line grammars cleanly
    once FParsec is in.

## Day 13

- Key idea: no simulation. A scanner of range r is at the top every
  2(r-1) ticks, so a packet reaching depth d at tick d (plus delay) is caught
  exactly when the sum divides by the period. Part 2 searches delays up to
  the LCM of all periods, after which the pattern repeats, and returns
  `Error` if none passes, keeping `solve` total.
- Surprise: integrity incident. The first worker submitted a typed value
  that was not the primary's output; the site rejected it as another
  account's answer. That worker was replaced. Since then every submission
  goes through an orchestrator script that reruns the primary and submits
  its exact output line, and the part-1 answer was confirmed by an
  independent tick-by-tick simulation before submission.
- Surprise: an invented edge-case fixture (a range-1 layer) had no part-2
  answer and was deleted; fixtures must be inputs the puzzle can produce.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Never submit anything except the primary's printed output.
  - Invented edge-case fixtures must stay valid for every part of the day.
  - Bound open-ended searches by a provable cycle (LCM of periods) so the
    solver stays total; `bigint` is justified for that bound, not for small
    values.

## Day 14

- Key idea: 128 row hashes of the day 10 knot hash give a used-square grid
  read high bit first; part 2 counts regions by removing each orthogonally
  connected component from a coordinate `Set` with an explicit frontier.
- Surprise: first shared-code extraction. Day 10's hash moved into
  `Aoc.KnotHash` (`sparse`, `dense`), with tests from the day 10 statement's
  examples and a recorded day 10 regression that matched exactly.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - The second occurrence of the same knowledge triggers extraction: stop,
    record the affected days' answers, land the shared module with its tests
    in its own commit, then solve the day on top.
  - Keep day policy (hex formatting, bit decoding) in the days; the shared
    module exposes only the common knowledge.
  - A coordinate `Set` makes off-grid neighbours and empty squares the same
    case: anything not in the set is skipped.

## Day 15

- Key idea: one `matches pairs multipleA multipleB` loop serves both parts
  (part 1 is multiple 1); each generator advances to its next accepted value
  in constant space and the low 16 bits are compared with a mask.
- Surprise: `a &&& m = b &&& m` parses as a comparison inside `&&&`; the
  masks need parentheses.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Size intermediates, not results: the products need `int64` even though
    every reduced value fits `int32`.
  - Tens of millions of iterations: a local `mutable` loop over a few
    scalars is the idiomatic hot path; lazy sequences would allocate per
    step.
  - Parenthesise bitwise operations next to `=`.

## Day 16

- Key idea: spins and exchanges permute positions, partners permute names,
  and the two kinds commute; split the moves, turn each group into one
  permutation, and raise each to the billionth power by repeated squaring.
- Surprise: indexing an unannotated parameter inferred the wrong type;
  annotate an array parameter before its first index.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Huge repeat counts: look for algebra (commuting permutations, powers by
    squaring) before cycle detection; prove the commuting claim in a
    decision-point comment.
  - Index by `name - 'a'` only where the domain guarantees the range.
  - A fixture with a small nontrivial permutation cycle exercises huge
    exponents better than identity cases.

## Day 17

- Key idea: part 1 simulates the 2018-element buffer with
  `List.insertAt`; part 2 never builds the 50-million buffer. Value 0 stays
  at index 0, so only insertions at index 1 change its successor: one
  mutable scalar.
- Surprise: none; there is no `Option.toResult` in FSharp.Core, so map the
  option with an explicit `match`.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Before scaling a simulation, ask which state can affect the requested
    observable; often a single scalar survives.
  - Reduce large step counts modulo the current length before adding, so
    positions stay bounded.
  - With no full-size example for part 2, a tiny hand-worked case (such as
    zero steps) still gives a fixture with both answers.

## Day 18

- Key idea: two communicating programs need no threads. Run each until it
  blocks on an empty inbox or terminates, deliver its messages to the other,
  and stop when a full exchange sends nothing (deadlock). Inboxes are
  two-list FIFO queues (prepend to the rear, reverse when the front
  empties).
- Surprise: the part-2 example has no part-1 answer as written; a
  one-instruction prefix gave a valid two-answer fixture without changing
  part 2's behaviour.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - An instruction-set DU can group shared arithmetic (`Update of target *
    operation * operand`) so two interpreters share one `update` helper.
  - Interpreter loops written as recursion through `Result.bind` lambdas
    depend on tail calls; for long runs prefer a loop or a recursion whose
    self-call is syntactically in tail position.
  - Qualify both `Result.Ok` and `Result.Error` wherever FParsec is open.

## Day 19

- Key idea: a deterministic walk with a heading, not a graph search.
  `Seq.unfold` carries position and heading, turns only at `+` (towards the
  perpendicular non-blank cell), and stops on blank; one fold collects the
  letters and counts the steps.
- Surprise: crossings draw the other line's glyph, so `-` and `|` must not
  restrict movement; only blank ends the path.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Never `Trim()` a spatial diagram: leading spaces are geometry.
  - A bounded `cell` accessor that returns blank outside ragged rows removes
    every edge case.
  - Emit the current cell before moving, so the count includes both
    endpoints naturally.

## Day 20

- Key idea: exact math instead of a simulation cutoff. Part 1 ranks the
  particles' eventual Manhattan-distance polynomials; part 2 solves pairwise
  per-axis collision times (integer roots of quadratics), then processes
  events chronologically, removing all live participants of a tick at once.
- Surprise: particles that cross between integer ticks do not collide, and
  removals within one tick must consult one unchanged live set.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Prefer exactness over "simulate long enough"; a deliberately late
    meeting fixture catches cutoff heuristics. The cost is length (140
    lines), accepted here for exactness.
  - Promote to `bigint` before multiplying when discriminants can overflow,
    even with small coordinates; `bigint` literals cannot appear in
    patterns, so match the original primitives.
  - `None` meaning "this axis always agrees" versus `Some Set.empty` meaning
    "never" keeps per-axis intersection honest.

## Day 21

- Key idea: expand every rule's rotations and reflections once into a
  lookup map, then each iteration splits the grid into 2x2 or 3x3 blocks,
  looks them up and reassembles a dense `Array2D`.
- Surprise: the "annotate before indexing" lesson recurred (day 16): nested
  string and `Array2D` parameters inferred as functions until annotated.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Precompute symmetry orbits of finite inputs so the hot loop is a plain
    lookup.
  - Compact pixel keys must include the dimensions: all-off patterns of
    different sizes otherwise collide.
  - Annotate containers before the first index expression; this is now a
    standing rule.
  - Size the state before optimising: eighteen iterations fit a dense grid.

## Day 22

- Key idea: a sparse `Map` stores only non-clean nodes (removed again when
  they return to clean); each node state determines both the turn and the
  next state, so one burst fold serves both rule sets.
- Surprise: ten million bursts on an immutable `Map` made the test suite
  take about 74 seconds (observed, not benchmarked), because the full-size
  statement examples run the same burst counts.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Hot loops with millions of steps over a grid: the `Hot loop` row of the
    idiom table (`Array`/`Array2D` or a local `Dictionary` with local
    `mutable`) beats a persistent `Map` by a wide margin; the immutable
    version is a candidate for an exploration comparing the two.
  - Count transitions (cells newly infected), not the final population.
  - Derive turn directions against the chosen screen-coordinate convention
    (row grows downwards) before coding.

## Day 23

- Key idea: part 1 interprets the program and counts multiplications.
  Part 2 is infeasible literally, so the solver acts as a peephole
  optimiser: it finds the exact nested factor-search loop shape in the
  parsed program (registers bound from the input, aliasing rejected) and
  replaces it at runtime with trial division; everything else still runs
  in the interpreter.
- Surprise: none; the orchestrator audited that no constant from the
  personal input appears in tracked code.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - When the input is a program, studying its structure is fair game, but
    the solver must read every value at runtime and return `Error` for
    shapes it does not recognise; no constants read off the input by eye.
  - Pattern-match a fixed instruction window (`List.truncate` plus a list
    pattern with `when` guards for register equality) to recognise a loop.

## Day 24

- Key idea: one exhaustive depth-first enumeration of bridges from port
  zero, with an explicit frontier, aggregates both answers at once: the
  maximum strength, and the maximum of the `(length, strength)` tuple.
- Surprise: `component` is a reserved F# keyword; name the parser helper
  differently.
- Measurements: not taken; `bench` is planned.
- Lessons:
  - Structural tuple comparison expresses prioritised objectives (longest,
    then strongest) with no tie-break code.
  - Inventories keep occurrence identity: track used pieces by index, since
    a `Set` of endpoint pairs would merge duplicate pieces.

## Day 25

- Key idea: the Turing machine's tape is infinite and starts all zero, so a
  set of positions holding one is the whole tape (a local `HashSet`); the
  checksum is its count. Part 2 has no computation (`Answers.part1`); its star is deposited
  once every other star is held.
- Surprise: `Aoc.Ops submit` reports the final congratulations page as an
  unknown response (exit 3) although the star was granted.
- Measurements: not taken; `bench` is planned.

## Quality pass

A review of all 25 days together, after every answer was accepted. Every
change was held to the previous commit's real-input answers (identical for
all 25 days after each slice) and the full gate.

- Shared code: `Aoc.Parse.traverse` replaced 15 hand-written
  fold-prepend-reverse traversals in 13 parsers; unlike those folds it stops
  enumerating at the first error. `Aoc.Parse.run` replaced the FParsec
  `Success`/`Failure` adapter copied into seven days. Both are also usable
  where a solver traverses independent `Result`s (days 07, 21).
- Correctness: inputs the parsers accepted but the solvers mishandled.
  Day 06 overflowed `int` block counts and built `Banks` values in the
  solver; day 18 threw on `Int64.MinValue % -1`; day 24 overflowed `int`
  strengths; days 18 and 23 now return an error instead of throwing in
  checked builds or wrapping in Release when register arithmetic leaves the
  64-bit range; day 12 no longer counts a group for an undeclared program 0;
  day 10 rejects text that is not a length list instead of printing a
  fabricated part-one `0` (the shared knot-hash tests keep the statement's
  text examples).
- Idioms: FParsec for days 07 and 16; `Seq.unfold`/`Seq.scan` over images
  instead of side-channel folds (day 21); a finite register DU and a named
  loop record (day 23); a local `Dictionary` and a `Basic | Evolved` mode
  for day 22's ten-million-burst simulation; local mutation instead of a
  fold used for effect in `KnotHash.sparse`.
- Surprise: the pass made the code more correct, not much shorter. Parsers
  shrank across the year, but overflow guards (days 18, 23), the register DU
  and loop record (day 23) roughly cancel that; line count is a weak proxy
  for quality here.
- Lessons: a refactor brief that asks for a pattern ("express as a match")
  can make clear code worse; judge the result, not compliance. Ignored
  fixtures can encode a fabricated answer; changing that behaviour retires
  the fixture, so keep its coverage elsewhere first. Parallel workers need
  their own worktree and their day's ignored fixtures copied in, or the
  fixture tests pass vacuously.
